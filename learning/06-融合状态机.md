# 06 · 融合状态机（核心）

这是整个项目最值得读的部分，也是唯一"没有标准答案、全是设计取舍"的部分。

对应代码：`tracker/CascadeMatchTracker/tracker.py`（约 1160 行）、`kalman.py`、`type.py`、`guess_pts.py`。

## 0. 先建立三个不变量

读这个状态机，只要记住三句话，剩下的都是细节：

1. **一个身份（class_id）一帧最多匹配一次。**
2. **一辆车（car_index）一帧最多匹配一次。**
3. **一个雷达点（lidar_index）一帧最多匹配一次。**

所有匹配阶段都靠 `used_classes` / `used_cars` / `used_lidar` 三个集合强制这些互斥关系。级联的"级"就是**优先级**：越靠前的阶段越"确定"，先用先得，后面的阶段只能用剩下的。

## 1. 数据结构

### 1.1 TrackingState —— 一个身份的全部状态

10 个固定身份，每个一个 `TrackingState`（`type.py` L171）。它把「我是谁」和「我在哪」**拆成两个独立的枚举**：

```python
identity_state: UNSEEN | GUESSED | CONFIRMED   # 身份有多确定
spatial_state:  UNINITIALIZED | TRACKING | COASTING | LOST   # 位置有多确定
frame_source:   本帧位置从哪来（10 种，见下表）
```

**为什么拆开？** 因为这两件事确实会独立变化：
- 身份确认了，但这一帧雷达没测到它 → `identity=CONFIRMED, spatial=COASTING`
- 只有雷达点，完全不知道是谁 → `identity=GUESSED, spatial=TRACKING`

混在一起的单一状态机做不到这种表达。

### 1.2 位置来源 `FrameSource`

| 枚举 | 含义 | 优先级 |
|---|---|---|
| `ALLY_LIDAR` | 己方反馈 + 雷达点验证 | 0（最可信） |
| `ALLY_FEEDBACK` | 只用己方反馈 | 1 |
| `CAMERA_LIDAR` | 彩色视觉身份 + 雷达点 | 2 |
| `GRAY_CAMERA_LIDAR` | 灰甲维持已确认身份 + 雷达点 | 3 |
| `LIDAR_HISTORY` | 历史轨迹与雷达点匈牙利匹配 | 4 |
| `GRAY_RADAR_GUESSED` | 灰甲模糊猜测 | 5 |
| `RADAR_GUESSED` | 纯雷达点猜测 | 6 |
| `KF_PREDICTED` | 卡尔曼外推 | 7 |
| `FIXED_GUESSED` | 长期丢失后的固定点 | 8（最不可信） |
| `INVALID` | 无效 | 9 |

`SOURCE_PRIORITY` 这张表定义了"可信度排序"，UI 用它决定颜色，裁判消息用它决定是否上报。

### 1.3 观测 `CarObservation`

检测结果被转换成不可变的 `CarObservation`（`tracker.py::_build_car_observations()`）：

| 字段 | 含义 |
|---|---|
| `car_index` | 本帧第几辆车（互斥用的键） |
| `car_box` / `car_confidence` | 车辆框 |
| `bot_id` | BoT-SORT 跨帧 ID |
| `armor_observations` | 全部装甲候选 |
| `selected_armor` | 选中的那个（含颜色、数字、两个置信度） |
| `semantic_candidates` | 可能的 class_id 元组 |
| `ray_world_3d` / `ray_uwb_2d` | 射线投影点（世界系 / 己方视角） |

`semantic_candidates` 的含义很关键：

```python
if 0 <= raw_class_id <= 9:      # 彩色：唯一
    semantic_candidates = (raw_class_id,)
elif 10 <= raw_class_id <= 14:  # 灰色：两个可能
    semantic_candidates = (raw_class_id - 10, raw_class_id - 5)   # 例如 G1 → (1, 6) 即 B1 或 R1
```

**灰甲一行代码就把阵营歧义编码进了数据结构**，后面的灰甲匹配阶段就是在解这个歧义。

## 2. 卡尔曼滤波器

`kalman.py::KalmanFilter2d`，状态向量 4 维：

```text
x = [x, y, vx, vy]
```

匀速模型：

```text
F = [[1,0,dt,0], [0,1,0,dt], [0,0,1,0], [0,0,0,1]]
H = [[1,0,0,0], [0,1,0,0]]
Q = q_std² · [[dt⁴/4,0,dt³/2,0], [0,dt⁴/4,0,dt³/2], [dt³/2,0,dt²,0], [0,dt³/2,0,dt²]]
```

参数：

| 参数 | 值 | 含义 |
|---|---|---|
| `process_q_std` | 2.0 | 过程噪声：假设机器人加速度有多剧烈 |
| `lidar_r_std_m` | 0.20 | 雷达测量噪声 σ（米） |
| `initial_position_std_m` | 0.25 | 初始位置不确定度 |
| `initial_velocity_std_mps` | 2.0 | 初始速度不确定度 |
| `hard_reset_distance_m` | 2.5 | 新测量离预测超过此值 → 重建滤波器 |
| `default_dt_sec` | 0.0333 | 默认 dt（30 FPS） |
| `min_dt_sec` / `max_dt_sec` | 0.001 / 0.20 | dt 钳位 |

三个设计点值得注意：

**① `q_std = 2.0` 偏大。** 这意味着滤波器认为"机器人可能急加速"。机器人确实会突然启停，所以宁可信其能变，不要太平滑。副作用是位置抖动会大一些。

**② `r_std` 可以逐次传入。** `update(pos, r_std=...)`：雷达更新用 0.20m，己方反馈用 `feedback_r_std_m + age × age_r_std_per_sec`（当前两者都是 0，即完全相信己方反馈）。

**③ `hard_reset()` 而不是 `update()`。** 当检测到"身份刚刚确认"或"位置跳变 ≥ 2.5m"时，直接重置状态向量（速度清零、交叉协方差清零），而不是让卡尔曼用增益去慢慢拉。理由在源码注释里：

> 避免旧轨迹错误拖拽新目标

举例：一个 GUESSED 轨迹被错误地放在场地左半场，突然相机确认它其实在右半场——如果只是 `update()`，卡尔曼会因为 `P` 已经收敛得很小而在几十帧内都拉不过去。`hard_reset` 直接跳过去。

**④ 有一个纯 NumPy 的兜底实现。** `try: from filterpy.kalman import KalmanFilter / except ImportError: class KalmanFilter:`——没装 `filterpy` 也能跑。而且兜底版用了 **Joseph 形式**更新协方差，注释说明原因：

> Joseph 形式在 R=0 的精确 0x02BB 更新下更稳定

## 3. 单帧流程：十个阶段

入口 `process_observations()` L1001。下面是完整的级联顺序，**这就是这个算法的骨架**：

```text
10.1  雷达输入整理（时效 + 坐标镜像 + 场界过滤）
10.2  全部目标的二维卡尔曼预测
10.3  BoT-ID 语义历史更新
10.4  己方哨兵反馈匹配 → 剔除己方雷达点
10.5  彩色相机-雷达三元组匹配          ★ 主匹配
10.6  灰色装甲身份维持匹配
10.7  旧猜测抢占标记
10.8  敌方历史轨迹 ↔ 雷达点匈牙利匹配
10.9  灰色装甲模糊猜测匹配
10.10 纯雷达目标猜测
10.11 未匹配目标：续航 / 固定点 / 无效化
10.12 输出有效性整理
```

下面逐个展开。

### 3.1 (10.1) 雷达输入整理

```python
if now - snapshot.received_monotonic > 0.20:  return []   # 过期
if not (0 <= x <= 28 and 0 <= y <= 15):       continue    # 场界外
if faction == BLUE: x, y = 28 - x, 15 - y                 # 阵营镜像
```

三条过滤之后，雷达点才进入后续逻辑。**过期就当作"没有雷达点"处理**，而不是用旧点——这是软同步的正确做法。

### 3.2 (10.2) 卡尔曼预测

```python
for track in self.tracks:
    track.begin_frame()          # 清空本帧输出
    if track.kalman_initialized:
        predicted, _ = track.kalman_filter_2d.predict(dt=dt)
        track.output_position_2d_m = predicted
```

`dt` 用实际帧间隔并钳位到 [0.001, 0.20]。**先预测后观测**，符合标准卡尔曼流程。

### 3.3 (10.3) BoT-ID 语义历史

维护 `bot_id → BotIdTrack` 的映射，记录这个"物理车辆"最近 30 帧看到过什么装甲。

```python
history.update(raw_class_id, combined_confidence, frame_index)
# 指数衰减加权
weight = exp(-decay_tau × age) × confidence
```

当前 `decay_tau=0.5`，`matching_window=10`（只取最近 10 帧算分布）。

**这个历史目前只是记录，未被匹配阶段直接使用**（`get_class_id_exponent_confidence()` 没有被调用）。它更像是为后续版本准备的基础设施——读代码时不要以为它参与了当前决策。

超过 `association_ttl_frames=30` 帧没出现的 `bot_id` 会被删除，同时清掉相关 track 的 `associated_bot_id`。

### 3.4 (10.4) 己方哨兵反馈匹配

**这一步的特殊之处：它先说话，后面的阶段都不能再用它占过的雷达点。**

```python
if 反馈年龄 > 0.15s: return                    # 无新鲜反馈 → 完全跳过
for ally_class in 己方 5 个身份:
    point = positions[role]                    # 来自裁判系统 0x02BB/0x0301
    if 距离 < 1.5m 的雷达点存在 → ALLY_LIDAR   # 反馈 + 雷达双确认
    else                        → ALLY_FEEDBACK # 只有反馈
    used_classes.add(ally_class)
```

**为什么己方优先？** 因为我们确切知道己方机器人在哪（裁判系统广播的），如果一个雷达点被己方占着，那它就不该被敌方身份抢走。这是消除一类常见误匹配的最便宜手段。

**己方反馈过期时有一个很强的保护**：

```python
# 己方 0x02BB 过期后，旧己方历史/KF 必须完全退出雷达关联。
if class_id in ally_classes and track.kalman_initialized:  # 在灰甲阶段
    continue
```

即：己方目标没有新鲜反馈时，**不参与随机分配**，也不允许旧的己方轨迹去占雷达点。原因很实际——己方机器人不在视野里时，它的旧轨迹可能正好落在敌方机器人的雷达点上，如果不排除，猜点会系统性出错。

### 3.5 (10.5) 彩色三元组匹配 ★ 主匹配

这是整个算法最有特色的地方。先看它解决什么问题。

**问题**：一辆车可能被检成多个框（虽然实际上很少），一个身份可能对应多个框，一个框附近可能有多个雷达点。如果简单做"框→最近雷达点"，会违反互斥性。

**方案**：构造三元组 `(class_id, car_index, lidar_index)`，然后**全局互斥求解**。

候选生成（`_build_colored_triplets()` L619）：

```python
for 每个车:
    if 车已被用 or 没选中装甲 or 装甲是灰色:  skip
    if 组合置信度 < 0.30:                    skip
    if 没有投影点 or semantic_candidates 不是唯一:  skip
    class_id = semantic_candidates[0]
    for 每个未用的雷达点:
        distance = ||投影点 - 雷达点||
        if distance > 1.5m:  skip
        cost = 2.0 × (1 - 组合置信度) + 6.0 × (distance / 1.5)
```

代价函数两项：

| 项 | 权重 | 含义 |
|---|---|---|
| `1 - 组合置信度` | 2.0 | 语义越不确定越贵 |
| `distance / gate` | 6.0 | 投影点离雷达点越远越贵（归一化到 0~1） |

**距离权重 6.0 是语义权重 2.0 的三倍**，说明作者更相信"位置应该对得上"而不是"语义置信度"。

求解（`_solve_disjoint_triplets()` L461）：**带记忆化的精确搜索**，不是匈牙利。

```python

    # 按 car 顺序推进；每个 car 要么不选，要么选一个未占用的 (class, lidar)
    # key = (-匹配数量, 总代价, 排序后的三元组)  ← 字典序比较
```

比较键的第一位是 `-len(selection)`，即**优先匹配数量多**，数量相同再比总代价，最后用确定性排序保证可复现。

**为什么用精确搜索而不是匈牙利？** 因为这是三维匹配，标准匈牙利只能解二维。这里的三元组规模很小（≤10 个身份 × ≤10 辆车 × 少量雷达点），搜索空间可控。

**作者自己的注（`docs/融合定位算法说明.md` 5.3 节）**，很值得看：

> 后续发现，训练好的模型在合适的阈值下并没有出现多个视觉框指向同一个 id 的情况，故实际情况恰好退化为了二元组，可以改为匈牙利匹配。但由于其本身时间代价已经极小，为了稳定性仍保留。

也就是说：**这个三元组求解在实践中几乎总是退化成二元组**，但作者保留它作为安全网。看到这段你会明白，为什么这里的代码比"实际需要"复杂——这是比赛场景下"宁可有保险"的取舍。

提交（`_commit_colored_matches()` L653）：

```python
track.identity_state = CONFIRMED
hard = (原身份是 UNSEEN 或 GUESSED) or (与预测距离 >= 2.5m)
self._set_measurement_output(track, 雷达点, CAMERA_LIDAR, r_std=0.20, hard_reset=hard)
```

**注意位置用的是雷达点，不是投影点。** 这是全系统的核心取舍。

### 3.6 (10.6) 灰甲身份维持

灰甲不知道阵营，但**如果某个身份已经被确认为 CONFIRMED，灰甲可以用来维持它**。

```python
for 每个灰甲观测:
    for class_id in semantic_candidates:       # 例如 G1 → (1, 6)
        if class_id 是己方 → skip               # 不让灰甲维持己方
        if track.identity != CONFIRMED or 未初始化 → skip
        if 距离（投影点）> 1.5 or 距离（预测位置）> 2.0 → skip
        cost = 1.5 × (1-置信度) + 2.0 × (轨迹距离/2.0) + 3.0 × (投影距离/1.5)
```

代价里有**两项距离**：一项是"投影点到雷达点"，一项是"卡尔曼预测到雷达点"。因为灰甲没有阵营信息，只能靠历史轨迹帮忙判断——如果预测位置也对得上，就更可信。

`1.5` 的语义权重比彩色阶段的 `2.0` 低，因为灰甲本身信息量就少。

**为什么禁止灰甲维持己方？** 己方位置由裁判系统精确给出，不需要靠灰甲来"帮忙"，而且灰甲的阵营歧义可能让己方身份被错误地挪到敌方位置。

### 3.7 (10.7) 旧猜测抢占标记

这一步不产生任何输出，只是打个标记：

```python
for 敌方 GUESSED 轨迹:
    if 离某个雷达点 < 2.0m 且 该雷达点本帧被彩色匹配占用:
        track.preempted_this_frame = True
```

作用：**防止一个已确认身份的雷达点被一个"猜"出来的身份抢走**。这些被打标记的轨迹在 10.10 的纯雷达猜点里会被跳过。

这是处理"猜测污染"的一个细节——猜点本身是不得已的，但不能让猜点去覆盖确认信息。

### 3.8 (10.8) 历史轨迹 ↔ 雷达点匈牙利匹配

视觉暂时失效时，已确认的敌方轨迹还能靠"预测位置"续接雷达：

```python
rows = 未匹配的敌方 class 且 卡尔曼已初始化
cols = 未使用的雷达点
cost = 距离 / 2.0,  valid = (距离 <= 2.0)
```

求解用 `_solve_partial_rows()` —— 这是标准的**匈牙利 + 虚拟列**技巧：

```python
matrix = np.full((rows, cols + rows), invalid_cost)    # 每个 row 一个虚拟列
matrix[:, :cols] = where(valid, costs, invalid_cost)
matrix[row, cols + row] = unmatched_cost               # 100.0
linear_sum_assignment(matrix)
```

**为什么加虚拟列？** 因为 `scipy.optimize.linear_sum_assignment` 求解的是"完美匹配"，如果行数 > 列数会直接报错或强制匹配。加虚拟列 + 高代价 `unmatched_cost`，就允许某些行"选择不匹配"。`invalid_cost = 1e6` 保证非法边永远不会被选（除非真的没得选）。

这个技巧在后面的猜点阶段也会复用，值得记住。

提交时：`frame_source = LIDAR_HISTORY`，并且**只有 CONFIRMED 身份才会给雷达点上色**：

```python
if track.identity_state == CONFIRMED:
    self._matched_lidar_classes[lidar_index] = class_id
```

源码注释解释了：猜测身份即使靠历史位置续接到雷达，UI 上仍显示为绿色「猜点」，只有确认身份才染阵营色。

### 3.9 (10.9) 灰甲模糊猜测

到这里还没配上的灰甲，就只能**猜阵营**了：

```python
for 未匹配的灰甲车:
    for class_id in semantic_candidates:
        if track.identity not in (UNSEEN, GUESSED):  skip
        if class_id 是己方 且 卡尔曼已初始化:        skip
        ...
        cost = 1.5 × (1-置信度) + 2.0 × track_cost + 3.0 × ray_distance/1.5
```

其中：

```python
track_cost = 0.5                                        # UNSEEN 或无历史
           = 轨迹距离 / 2.0                              # 有历史（且门限 2.0）
```

然后是一个**阵营偏置**处理：

```python
opposite = class_id + 5 if class_id < 5 else class_id - 5   # B1 ↔ R1
opposite_cost = base_candidates.get((opposite, car_index, lidar_index))
if class_id 是敌方 and opposite_cost 存在 and |base_cost - opposite_cost| <= 0.15:
    total -= 0.05      # enemy_tie_bias
```

含义：当 **B1 和 R1 的代价几乎一样**（差 ≤ 0.15）时，略微偏向敌方假设。
理由很实际：雷达站关注的是敌方，猜成敌方更有用；猜错了代价也可接受。

匹配结果的身份状态是 `GUESSED`（不是 CONFIRMED），且 `hard_reset=True`。

### 3.10 (10.10) 纯雷达猜点

完全没有视觉证据时，把剩下的雷达点**分配**给敌方身份：

```python
available = 未使用的雷达点
eligible = [敌方 class 满足以下之一]
    group 0: identity == UNSEEN
    group 1: continuous_loss_count + 1 >= 10
排序键 = (group, -continuous_loss_count, role_rank[角色], class_id)
selected = 前 len(available) 个
```

角色优先级：

```yaml
guessing:
  enemy_only: true
  role_priority: ["hero", "standard_3", "standard_4", "sentry", "engineer"]
```

即：英雄 > 3 号 > 4 号 > 哨兵 > 工程。理由大概是"英雄威胁最大，工程最可能在后方"。

分配代价是个**非常巧妙的写法**：

```python
cost = 0.0 if 雷达点在"偏好半场" else 1.0
     + rng.random() * 1e-6          # 随机 tie-break
```

其中"偏好半场"是：蓝方身份（class < 5）偏好 `x >= 14`，红方偏好 `x <= 14`——即**优先猜在敌方半场的点**。

随机项只有 1e-6，作用是"在同等条件下随机选一个"，但用**固定种子** `random_seed: 2026`，所以结果可复现。这个细节很讲究：既避免了"永远选 index 0"的系统性偏差，又保证了测试可重复。

### 3.11 (10.11) 未匹配目标处理

```python
pending = unseen_frame_count + 1   if UNSEEN
        = continuous_loss_count + 1  otherwise

if pending >= 30:
    point = PointGuesser.predict_points(track, ref_color)
    → FIXED_GUESSED（固定回退点）
elif kalman_initialized:
    → KF_PREDICTED，spatial = COASTING (pending < 10) 或 LOST
else:
    → INVALID（从未定位过，无法输出）
```

**非敌方身份（己方）在这里被直接置为无效**：

```python
if track.class_id not in enemy_classes:
    ... output_valid = False
```

因为己方位置应该来自裁判系统反馈，不该由这个模块猜。

#### `PointGuesser` 的算法

`guess_pts.py`，配置在 `config/guess_pts.yaml`：每个机器人有 4~5 个"常见驻留点"。

```text
对每个候选点 p:
    d_vec = p - last_pos
    cos_sim = (v · d_vec) / (|v| |d_vec|)        # 速度方向与"指向该点"的余弦相似
    d_score = exp(-|d_vec| × 0.01)               # 距离越近分越高
    score   = 0.003 × cos_sim + 0.997 × d_score
选 score 最大的点
```

权重 0.003 vs 0.997 —— **几乎完全按距离，方向只是一个极弱的先验**。所以这个模块的本质是"回到最近的那个常见驻留点"。

`cos_factor: 0.003` 这个数字小得有点反直觉，可能是调参的结果。如果你要改，建议先理解原意再动。

### 3.12 (10.12) 输出整理

```python
for track:
    lidar_miss_count = 0 if 来源∈雷达类 else +1
    continuous_loss_count = 0 if 来源∈(雷达类 ∪ ALLY_FEEDBACK) else +1
    unseen_frame_count   = +1 if (UNSEEN 且 来源∉雷达类) else 0
    output_valid &= 坐标有限
```

`latest_lidar_matches` 只包含**真实匹配**（不包含猜点），UI 和调试据此给雷达点上色。

## 4. 完整代价函数速查

| 阶段 | 代价公式 | 门限 |
|---|---|---|
| 己方反馈 | `dist / 1.5` | 1.5 m |
| 彩色三元组 | `2.0(1-C) + 6.0·d_ray/1.5` | d_ray ≤ 1.5 |
| 灰甲维持 | `1.5(1-C) + 2.0·d_track/2.0 + 3.0·d_ray/1.5` | d_ray ≤1.5, d_track ≤2.0 |
| 历史匈牙利 | `d / 2.0` | d ≤ 2.0 |
| 灰甲模糊 | `1.5(1-C) + 2.0·track_cost + 3.0·d_ray/1.5`（敌方同分时 −0.05） | d_ray ≤1.5, d_track ≤2.0 |
| 纯雷达猜 | `0`（偏好半场）/ `1`（另一侧）+ 1e-6·rand | — |

其中 `C` = 组合置信度 = `0.70 × 数字 + 0.30 × 装甲`。

## 5. 一个数值例子

假设场上真实情况：红方 3 号（R3）在场地 (12.0, 5.0)，蓝方视角运行。

```text
① 雷达给出一批点，其中一个 (11.9, 5.1)
② 相机检测到一辆车，装甲识别为「红 3」，digit_conf=0.9, armor_conf=0.8
   → C = 0.70×0.9 + 0.30×0.8 = 0.87
③ 射线投影得到 (12.3, 5.4)
④ 镜像到己方视角（蓝方）：(28-12.3, 15-5.4) = (15.7, 9.6)
⑤ 该雷达点镜像：(28-11.9, 15-5.1) = (16.1, 9.9)
⑥ d_ray = ||(15.7,9.6)-(16.1,9.9)|| ≈ 0.5 m，< 1.5 ✓
⑦ cost = 2.0×(1-0.87) + 6.0×0.5/1.5 = 0.26 + 2.0 = 2.26
⑧ 与其他候选比较，若代价最小 → 匹配成功
⑨ R3 的卡尔曼用 (16.1, 9.9) 更新，输出 = 滤波后的位置
```

注意 ⑦ 里**距离项（2.0）远大于语义项（0.26）**——即使语义置信度很高，位置对不上也会被拒。这正是这套算法的性格。

## 6. 设计取舍（作者自己说的）

`docs/融合定位算法说明.md` 里有两段「注」，是理解这个项目最好的材料：

**注 1（5.3 节）**：本来想用激进的 `(历史, 视觉, 雷达)` 三元组融合，但没有足够好的数据难以调试，所以退回**分阶段匹配**。

> 由于开发时还没有足够好的数据难以调试，故退而使用稳定性更高的分阶段匹配。

**注 2（5.3 节）**：彩色三元组在实践中退化为二元组，但为了稳定性保留。

这两句话解释了这个状态机为什么"看起来有冗余"：**它是为了可调试性和稳定性而牺牲了理论优雅**。这是比赛工程与论文算法的典型差别。
