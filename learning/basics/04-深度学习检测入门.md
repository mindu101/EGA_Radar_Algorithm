# 基础 04 · 深度学习检测入门（YOLO、TensorRT 与跟踪）

> 前提：你会用 OpenCV 做传统检测（模板匹配 `matchTemplate`、级联检测器
> `CascadeClassifier`、或 `cv2.dnn` 跑过现成模型）。这篇解释项目视觉链路
> 的三个新东西：YOLO 检测、TensorRT 部署、BoT-SORT 跟踪。

## 1. 从传统检测到 YOLO：到底变了什么

你在 OpenCV 里的检测经验大概是：**人设计特征 → 滑窗扫描 → 分类器判断**。
HOG + SVM 数行人、Haar 级联数人脸，都是这个套路。天花板在于**特征是人设计的**：
换个光照、换个视角、目标换个涂装，手工特征就崩。

深度学习只改了一件事：**特征也交给学**。

```text
传统:  图像 → [手工特征 HOG/Haar] → SVM 分类
现在:  图像 → [卷积网络: 自己学出来的特征] → 直接回归框和类别
```

卷积层你其实早就用过——`cv2.filter2D(img, kernel)` 就是一次卷积。CNN 的区别
只是这个 kernel 不再由你写，而是训练时从数据里学（上百万个可调参数）。
一张 4024×3036 的比赛照片里「红方 3 号车」长什么样，人工设计不出来，
但从几千张标注图里学得出来。

**YOLO**（You Only Look Once）是检测的主流结构：把图缩到固定输入（本项目车辆
检测用 1280×1280），网络一次前向就输出所有目标的框 + 类别 + 置信度：

```text
输出 (N, 6)：[x1, y1, x2, y2, conf, class_id]
```

对比滑窗法逐窗口分类，YOLO 一次看全图所以快——这也是名字的含义。
你不需要懂内部结构（anchor、FPN……）就能读懂本项目：把它当一个
**「图片进、框列表出」的黑盒函数**即可。

## 2. 训练 / 推理 / 部署链：.pt → ONNX → .engine

读项目 `weights/` 目录会看到同一模型有三种后缀，这是标准部署链：

```text
训练（别人电脑上, 需要标注数据 + GPU 数小时~数天）
   │  car_best.pt        PyTorch 权重，训练框架的格式
   ▼
导出（一次性）
   │  car_best.onnx      「通用中间格式」，任何框架都能读
   ▼
编译（目标 GPU 上, 分钟级）
      car_best.engine    TensorRT 引擎：针对本机 GPU 架构优化过的二进制
```

**TensorRT** 是 NVIDIA 的推理加速器：把网络结构重排、算子融合、精度降到 FP16
（半精度浮点，精度损失可忽略、速度约翻倍）。本项目在 RTX 5090 上跑三个模型
还敢用 4024×3036 的原图，全靠它。

⚠️ **新手最容易踩的坑**（根目录 README 特意写了）：`.engine` 和生成它的
GPU 架构 + CUDA + TensorRT 版本**强绑定**，换机器大概率加载失败。解法是用
同目录的 `.pt` / `.onnx` 在新机器上重新转换（`Main_ws/utils/convert_pt2tensorrt.py`）。

## 3. 本项目的三个模型和 A/B 流水线

| 模型 | 类型 | 输入 | 输出 | 配置 |
|---|---|---|---|---|
| `car/best.engine` | YOLOv12 检测 | 整图 1280×1280 | 车辆框 + track_id | `armor_detector.*` |
| `armor/armor_best.engine` | 装甲板检测 | 车辆 ROI 裁小块 192×192 | 装甲框 | `armor_detector.*` |
| `MobileNetv2.2.pth` | 数字分类 | 装甲小图 | 15 类身份之一 | `digit_detector.*` |

为什么拆成两级（A/B 流水线，详见 [../02-架构与数据流.md](../02-架构与数据流.md)）？
全图太贵，先 A 阶段找车（大模型一次），B 阶段只对每辆车的 ROI 做装甲 + 数字
识别（小模型多次）。两级之间是「容量为 1 的邮箱」：B 没处理完时 A 的新帧直接
覆盖旧的——**保低延迟，弃个别帧**。

15 个 class_id 的含义（`params.yaml: class_names`）：

```text
0-4  = B1 B2 B3 B4 B7     蓝方英雄/工程/步战/哨兵...(ID 简写)
5-9  = R1 R2 R3 R4 R7     红方对应
10-14 = G1 G2 G3 G4 G7    灰色/无灯装甲（分不清敌我时先给个中立身份）
```

身份由「装甲位置 + 数字分类」组合判定，置信度加权
`0.70 × 数字置信度 + 0.30 × 装甲置信度`。

## 4. 检测之外为什么还要「跟踪」

检测器只回答「这一帧里有什么」。但融合层需要「**上一帧的 R3 和这一帧的 R3
是同一个目标**」——跨帧的身份连续性。这就是多目标跟踪（MOT）。

最经典的组合（SORT / ByteTrack / BoT-SORT 都在此框架上）：

```text
1. 用卡尔曼预测每个已知 track 在当前帧的位置（基础 05 的内容）
2. 检测结果 vs 预测位置 建代价矩阵（位置距离 + 外观相似度）
3. 匈牙利算法求最优一对一分配（基础 05 + 实验 6）
4. 匹配上 → 更新该 track；检测没配上 → 新生 track；track 连续没匹配 → 删除
```

本项目 A 阶段内置 BoT-SORT（`model/yolov12/predictor_with_tracker.py`），
在**图像平面**上给车框稳定的 track_id；而融合层的 `CascadeMatchTracker`
在**场地平面**上做更重的身份管理——两层跟踪各管一层，别混淆。

## 5. 和 OpenCV 视觉的最后一点对照

| OpenCV 时代 | 本项目 |
|---|---|
| `matchTemplate` 找装甲板 | YOLO 直接出装甲框，抗光照/形变 |
| 颜色阈值判红蓝 | 灯条颜色 + 数字分类，还有灰甲兜底 |
| `cv2.calcOpticalFlow` 或 CSRT 跟单目标 | BoT-SORT 跟多目标 + 级联融合管身份 |
| `cv2.dnn.readFromONNX` CPU 推理 | TensorRT FP16 GPU 推理 |

值得先读的代码只有两处：`model/yolov12/predictor.py::predict_batch()`
（模型怎么被调用）和 `model/armor_detector.py`（两级检测怎么串起来）。
ultralytics 源码副本（`model/pfa_yolov5/`）**不要读**，那是不走的一条路。
