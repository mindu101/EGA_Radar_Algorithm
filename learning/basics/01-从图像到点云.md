# 基础 01 · 从图像到点云

> 前提：你会 OpenCV 的图像读写、阈值、滤波、找轮廓（`findContours`）。
> 这篇把「图像思维」翻译成「点云思维」，读完能看懂 Lidar_ws 里 C++ 代码在干什么。

## 1. 一张表翻译两个世界

图像和点云都是「传感器对三维世界的采样」，只是采样方式不同：

| | 图像（你熟悉的世界） | 点云（本项目雷达的世界） |
|---|---|---|
| 数据结构 | `H×W×3` 的规则网格，每个格子是像素 | `N×3`（或 `N×4` 带强度）的**无序点列表**，每行 `(x, y, z)`，单位是米 |
| 谁产生它 | 相机：一次曝光成像 | 激光雷达：每个点是一次测距（光飞出去、弹回来、计时） |
| 「邻居」概念 | 天然存在：`img[y, x+1]` 就是右邻 | **没有**：点 0 和点 1 可能隔 20 米，找邻居要靠 KD 树或体素网格 |
| 值域 | 0~255 的亮度/颜色 | 任意实数坐标，场地是 28m×15m，z 最高约 2.4m |
| 对应 OpenCV 操作 | `cv2.imread` | 没有 PLY/PCD 的直接支持，用 open3d 或 numpy 手读（见实验 1） |
| 遮挡 | 远处被近处挡住 | 同样有：激光打不到墙后面，产生「阴影区」 |
| 噪声 | 高斯噪声、坏点 | 测距噪声、玻璃/镜面打到奇怪的地方、雨雾鬼影 |

**最重要的一条**：图像上的操作（卷积、腐蚀）依赖网格结构；点云没有网格，所以一切
算法的第一步几乎都是**重建邻域**——KD 树（空间二分查找）或体素网格（把空间切成
小立方体当「像素」用）。理解了这一点，PCL 的函数名就都能猜到了。

## 2. 点云从哪来：Livox 的「非重复扫描」

传统机械雷达靠一排激光头 360° 旋转，扫出一圈一圈的环——同一角度每转回来一次，
采样密度固定。

本项目用的 **Livox HAP 是非重复扫描**：激光按一朵「玫瑰线」花瓣图案在一个约
几十度的视场里反复画圈。任何**一瞬间**只覆盖很稀疏的点，但**累积 100 ms、1 s**，
点会越铺越密，最终逼近照片级的覆盖。

这个特性直接塑造了项目里的两处设计（详见 [../03-雷达管线三节点.md](../03-雷达管线三节点.md)）：

- `localization` / `dynamic_cloud` 都要**累积多帧**才够密；
- 但机器人是动的，累积太久动态物体就拖影了——所以 `max_frames: 100`、动态点还有
  「近/中/远」三档不同累积时长的分区。

点云每个点除了 `(x, y, z)` 还常带：

- `intensity`：反射强度（类似图像的亮度，黑车和铝车反射不同，可用来区分材质）；
- `timestamp`：这个点精确的采集时刻（非重复扫描一帧里各点时刻不同，快速运动时
  要按时间补偿，术语叫 motion compensation / 去畸变）。

## 3. 你会的操作，点云世界都有对应物

| 你在 OpenCV 里会 | 点云世界的对应 | 本项目哪里用到 |
|---|---|---|
| `cv2.inRange` 颜色阈值分割 | 按距离/高度区间过滤点 | `dynamic_cloud` 的场地 ROI 过滤 |
| `cv2.GaussianBlur` 去噪 | 统计滤波 / 半径滤波剔除离群点 | 各节点预处理 |
| `cv2.resize` 缩图 | **体素下采样**（voxel grid）：每小立方体留一个点 | `localization` 配准前降规模 |
| `cv2.kmeans` / `floodFill` 连通域 | **欧式聚类**：距离小于阈值的点连成一团 | `cluster.cpp`（见实验 4） |
| 特征匹配 + `findHomography` 拼图 | **点云配准**（ICP / NDT）：求两个刚体变换对齐 | `localization` 的 GICP→NDT（见实验 7） |
| 背景扣除（`createBackgroundSubtractorMOG2`） | 用建好的静态地图扣除静态点，剩下的就是**动态目标** | `dynamic_cloud.cpp` 的核心 |
| `minAreaRect` 求目标框 | 求聚类的中心/包围盒 | `cluster.cpp` 输出聚类中心 |

背景扣除那条值得多说一句：项目里「动态点提取」和你在 OpenCV 里做运动检测
思路完全一样——先有一张背景（这里是提前建好的场地地图 `RMUC2026.pcd`），
当前帧与背景「相减」，剩下的就是动的东西。区别只是相减发生在三维坐标里：
把当前点云用 TF 变到地图坐标系，在地图附近一定半径内能找到邻居的点是「静态」，
找不到的是「动态」。

## 4. 点云的文件格式速查

| 格式 | 长什么样 | 项目里 |
|---|---|---|
| **PLY** | 文本头声明属性 + 二进制体，可存顶点+面（网格） | `Main_ws/field/RMUC2026.ply`（场地网格，104 万顶点） |
| **PCD** | PCL 自家格式，头 + 点数据 | `Lidar_ws/.../dynamic_cloud/config/RMUC2026.pcd`（点云地图） |
| **PointCloud2** | ROS2 话题上传输的二进制消息，`fields` 描述每个点有哪些字段 | `/livox/lidar` 等所有话题 |

实验 1 里我们手写过 PLY 读取器，你会发现它一点都不神秘：读文本头拿到
「有多少个点、每个点哪几个字段」，拼一个 numpy dtype，`np.fromfile` 一次读完。

## 5. 本项目点云数据流（先记骨架）

```text
/livox/lidar            雷达原始点云（livox_frame 坐标系，无序，每帧约 1~2 万点）
    │
localization            和静态地图配准，发布 TF：rm_frame → livox_frame
    │                    （= 告诉所有人：雷达自己架在场地哪个位置、朝哪）
dynamic_cloud           当前点云变换到 rm_frame → 扣掉静态地图 → 剩下的动态点
    │                    近/中/远三档不同累积时长（近处机器人动得快，不敢多积）
    │
cluster                 欧式聚类 → 每个聚类输出一个中心点
    │
/livox/lidar_cluster    Python 融合层拿到的就只有「几个中心点」了！
```

注意最后一行：**Python 侧根本不处理点云**，`Main_ws/driver/lidar/ros2_lidar_client.py`
订阅 `/livox/lidar_cluster`，把消息读成 `(x, y)` 列表缓存最新一份。所以学本项目
时，点云的难点全部集中在 Lidar_ws 的三个 C++ 节点里，而它们的原理就是上面
这张表 + 实验室里那几个实验。
