# 08 · 调试与验证

这篇是「怎么知道它跑对了 / 跑错了错在哪」。

先给结论：**不接硬件也能完整验证这套系统**。项目提供了同步回放链路，一键跑通相机 + 雷达 + 融合全部环节。

## 1. 最快的上手路线：同步回放

### 1.1 拿数据

完整数据在网盘（README 里有链接和提取码），解压到 `recordings/` 下：

```text
recordings/replay_sample/                 # 约 7 秒，快速检查
    camera/camera_record.mp4
    camera/camera_timestamps.csv
    camera/calibration_snapshot.yaml
    rosbag_livox_lidar/metadata.yaml

recordings/full_replay_20260808_153910/   # 约 9.9 分钟，完整复现
    ...
```

`recordings/` 在 `.gitignore` 里，不随仓库分发。

### 1.2 预检（只读，不动任何东西）

```bash
./run_replay_test.sh Main_ws/config/test.yaml --preflight-only
```

预检会检查：bag 与相机目录存在、时间戳单调递增、标定快照完整、**两段时间范围有交集**。
这一步失败就不用往下走了，错误信息很直接。

### 1.3 完整回放

```bash
./run_replay_test.sh Main_ws/config/test.yaml        # 7 秒样例
./run_replay_test.sh Main_ws/config/test_full.yaml   # 9.9 分钟完整数据
```

启动后的操作顺序（和真实比赛一致）：

```text
1. ROS 三个节点启动（不启动 Livox 驱动，点云来自 bag）
2. Python 主程序 + UI 启动
3. UI 显示回放区间的第一帧，等你标定
4. 点「直接导入外参」（回放数据自带标定快照）或手动标点
5. 可选勾选 xy maps
6. 点「启动雷达站」
7. 主循环写出 tracking.ready → 启动器才开始播 rosbag
8. bag 发布 /clock，相机线程按同一时钟发帧
9. 播放结束保留 UI（keep_ui_after_replay: true）
```

**第 7 步的顺序很讲究**：先等模型预热完成再开始播放，避免开头的帧被丢掉。这也是为什么启动时会觉得"卡了几秒才开始动"。

### 1.4 回放模式下的三个坑

| 坑 | 说明 |
|---|---|
| **内参不会读你的 params.yaml** | 回放**强制**用录像目录里的 `calibration_snapshot.yaml::intrinsics` 覆盖 `transform.K/dist_coeffs`。改 params.yaml 的内参在回放里无效 |
| **雷达参数读源码不是安装副本** | 回放读 `Lidar_ws/src/.../config/params.yaml`；正式启动读 `Lidar_ws/install/.../share/...`。改了源码配置忘了 `colcon build`，会出现"回放正常、比赛异常" |
| **`test.yaml` 的注释可能过时** | 例如 `replay_README.md` 写「faction 当前为 red」，但实际 `test.yaml` 里是 `blue`。**以 yaml 文件为准**，不要信文档 |

每次回放会在 `Main_ws/logs/replay/YYYYMMDD_HHMMSS/` 下生成：

| 文件 | 用途 |
|---|---|
| `runtime_params.yaml` | **本次实际生效的最终配置**（含所有覆盖） |
| `resolved_test.yaml` | 解析后的绝对路径、时间范围、起播偏移 |
| `tracking.ready` | 主循环就绪标记 |
| `ros_pipeline.log` / `python_app.log` / `rosbag_play.log` | 三路日志分开 |
| `runtime_metrics.jsonl` | 逐帧耗时与延迟（若开启） |

**排查参数问题的第一现场是 `runtime_params.yaml`**，不是原始 `params.yaml`。

## 2. RViz 里看什么

`launch_rviz: true` 时自动加载 `display_point_cloud_ROS2.rviz`。这张表是排查雷达链路的顺序：

| 话题 | 正常表现 | 异常说明什么 |
|---|---|---|
| `/livox/lidar` | 原始点云，随视角变化 | 没数据 → 驱动/回放问题 |
| `/livox/map` | 静态场地点云，稳定不动 | 没数据 → 地图未加载 |
| `/filter_map` | **配准实际用的点云** | 与 map 错位 → **定位偏了**（第一现场） |
| `/livox/registration_source` | 与 filter_map 相同 | 同上 |
| `/livox/lidar_dynamic` | 只有动的东西 + 拖尾 | 满地都是 → 静态扣除失效（定位偏了） |
| `/livox/lidar_cluster` | 每簇一个点 | 点太多 → 聚类太碎；没点 → 阈值太严 |

TF 树检查：

```bash
ros2 run tf2_tools view_frames        # 生成 frames.pdf
ros2 run tf2_ros tf2_echo rm_frame livox_frame
```

`rm_frame → livox_frame` 的平移应该接近 `lidar_extrinsics.yaml` 里的 `translation`（当前 `[0.0, 6.5, 3.8]`）。如果差很远，说明配准跑飞了。

### 2.1 一个更直观的判据

在 RViz 里同时加载 `/livox/map`（比如染成白色）和 `/filter_map`（染成红色）：

- 两者**重合** → 定位正确，动态点提取可信。
- 红色整体偏移 → 定位错，后面所有融合结果都不可信，别再往下查了。

这是最省时间的判断，**任何"目标位置不对"的问题都应该先做这一步**。

## 3. UI 里的耗时调试

`debug.timing_debug_enabled: true`，UI 里有个「耗时调试」窗口，`get_timing_debug_text()` 生成内容。

### 3.1 输出结构

```text
跟踪定位耗时调试（单位 ms，顺序为 last/EMA平均/历史最大）
单帧端到端延迟: 42.3 ms | 稳定提交间隔: 38.1 ms (EMA) | 稳定定位吞吐: 26.25 FPS
帧序号: 源 1204 / 提交 1188 | 待处理覆盖 16 | 过期丢弃 3

主循环最慢: 03 车辆检测与BoT-SORT avg 18.2 ms
跟踪器最慢: 10/彩色相机-雷达三元组匹配 avg 0.9 ms
检测器最慢: 06 装甲板与数字神经网络识别 avg 12.4 ms
异步可视化最慢: 12/后台合并可视化 avg 4.1 ms

按模块编号排序（已合并跨分区重复词条）
  01 获取并接纳最新相机帧: ...
  03 车辆检测与BoT-SORT: ...
  ...
```

`get_pipeline_module_text()` 里那 120 行编号表（01~12，带子编号 03.2.4.1.3）是**性能排查的字典**，值得花 10 分钟读一遍。它明确标了每个步骤是 CPU 还是 GPU、是"原子计时"还是"父级计时"、跨设备传输方向。

### 3.2 三个必须理解的指标

| 指标 | 定义 | 常见误读 |
|---|---|---|
| **单帧端到端延迟** | 该帧进入 A 阶段 → 模块 11 提交 | 不是吞吐的倒数 |
| **稳定提交间隔（EMA）** | 相邻两次提交的时间差，指数平滑 | 这才是吞吐口径 |
| **实际吞吐 FPS** | `1 / 提交间隔EMA` | **不能用 `1 / 单帧延迟` 代替** |

源码里专门写了一行说明：

> 说明：流水线 FPS = 1/提交间隔；不能用单帧总延迟的倒数代替。

原因：A 和 B 是重叠执行的，单帧延迟包含了等待时间，而吞吐反映的是提交节奏。**混用会得出"30FPS"的错觉。**

### 3.3 诊断计数器

同屏还会显示：

```text
待处理覆盖 pending_replaced_total   ← B 太慢，A 的包被覆盖
过期丢弃 stale_before_stage_b + stale_before_state   ← 数据太旧
```

| 现象 | 含义 | 对策 |
|---|---|---|
| 覆盖数持续增长 | B 处理不过来 | 降 `armor_detector.img_size`、换更快 engine、或干脆关流水线对比 |
| 过期丢弃多 | 端到端太慢/时钟异常 | 查 `input_frame_age_ms` 是否本来就大（相机侧延迟） |
| 两者都低但 FPS 低 | 相机本身帧率低 | 查 `device.yaml` 的 `acquisition_rate` 和曝光 |

## 4. 在线残差统计：判断标定质量

`projection_lidar_statistics` 是一个很实用的自检模块（`tracker/CascadeMatchTracker/projection_lidar_statistics.py`）。

### 4.1 它在做什么

只挑选**高可靠**的"投影点—雷达点"配对，统计它们的**残差分布**：

```yaml
projection_lidar_statistics:
  enabled: true
  include_gray_camera_lidar: false
  min_armor_confidence: 0.70
  min_digit_confidence: 0.70
  min_combined_confidence: 0.75
  max_match_distance_m: 0.75        # 配对的残差必须很小
  min_lidar_margin_m: 0.50          # 次近的雷达点必须远 0.5m 以上（排除歧义）
  min_camera_margin_m: 0.50
  max_lidar_ambiguity_ratio: 0.50   # d1/d_second 必须够小
  max_camera_ambiguity_ratio: 0.50
  min_sample_interval_sec: 0.20
```

只有同时满足「高置信度 + 距离近 + 没有竞争候选」的配对才被采纳。然后用 **Welford 在线算法**维护二维残差的均值、协方差，**不保存历史样本**（内存恒定）。

### 4.2 怎么用

UI 里能看到 `get_projection_lidar_statistics_text()` 的报告，含：

- 全局与分 class 的残差均值、标准差
- 被拒绝样本的分类统计（`REJECTION_LABELS`）
- 每类拒绝原因的数量

| 观察 | 结论 |
|---|---|
| 均值接近 (0, 0)，σ ≈ 0.2–0.5m | 标定良好 |
| 均值系统性偏离某方向 | 外参有偏（平移误差）|
| 均值随距离线性增长 | 内参/畸变有偏 |
| 拒绝率极高 | 门限太严，或标定已经坏了 |

**这是唯一一个能定量评价标定质量的机制**，比赛现场重新架设后一定要看一眼。

### 4.3 什么时候会清零

统计会在这些时候重置：外参更新、阵营变化、XY Map 开关、XY Map 重建完成/失败。
理由很简单：这些变化后旧样本不再可比。

## 5. 日志与指标

### 5.1 性能指标

```yaml
debug.performance_metrics:
  enabled: true
  output_path: "logs/performance/runtime_metrics.jsonl"
  flush_interval_sec: 1.0
  gpu_sample_interval_sec: 0.5
  queue_size: 512
```

JSONL 逐行写入，后台线程负责落盘，**主循环只做 submit，不阻塞**。每行包含：

```json
{
  "record_type": "frame",
  "frame_id": 1204,
  "input_frame_age_ms": 33.2,
  "end_to_end_latency_ms": 75.1,
  "processing_ms": 42.3,
  "commit_interval_ms": 38.1,
  "commit_fps": 26.25,
  "object_counts": {"detections": 6, "active_tracks": 6, "lidar_points": 7, "fly_points": 0},
  "stages_ms": {"stage_a": {...}, "stage_b": {...}, "pipeline": {...}},
  "pipeline": {"epoch": 1, "source_sequence": 1204, "commit_sequence": 1188, ...}
}
```

用 pandas 几行就能画图：

```python
import pandas as pd
df = pd.read_json("logs/performance/runtime_metrics.jsonl", lines=True)
df = df[df.record_type == "frame"]
df[["processing_ms", "commit_interval_ms"]].plot()
df["stage_a_ms"].hist(bins=50)
```

`Main_ws/statistics_README.md` 里有更完整的分析说明。

### 5.2 日志分散在三个地方

| 日志 | 位置 |
|---|---|
| ROS 节点（C++） | 终端 stdout / `logs/ros/` |
| Python 主程序 | 终端 / `Main_ws/logs/` |
| 回放三路分离 | `Main_ws/logs/replay/<时间戳>/*.log` |

**排查 ROS 侧问题时看 `ros_pipeline.log`，不要在 Python 日志里找。**

## 6. 测试

`Main_ws/tests/` 有 20 个测试文件，最有价值的三个：

| 测试 | 为什么值得跑 |
|---|---|
| `test_cascade_match_tracker.py` | **纯 CPU**，用 `CascadeMatchTracker.create_for_test()` 不加载 GPU 模型，直接测状态机。改融合逻辑后必跑 |
| `test_detection_pipeline_equivalence.py` | 验证流水线模式和串行模式输出等价 |
| `test_detection_pipeline_mailbox.py` | 验证邮箱的覆盖/关闭语义 |

跑法（在 `Main_ws` 下）：

```bash
cd Main_ws
python -m pytest tests/ -v
```

`create_for_test()` 这个设计很值得学：它绕过 `__init__` 里的模型加载，手工装配状态机所需字段。**测试不依赖 GPU，意味着 CI 能跑，也意味着你可以快速迭代算法。**

## 7. 常见故障速查

| 现象 | 最可能的原因 | 先查什么 |
|---|---|---|
| 启动就崩，报 engine 加载失败 | TensorRT engine 与 GPU/CUDA 版本不匹配 | 用 `.pt/.onnx` 重新转（`utils/convert_pt2tensorrt.py`） |
| 没有 `/livox/lidar` | Livox 驱动没起 / `start_livox` 为 false | `ros2 topic hz /livox/lidar` |
| 有原始点云但没有 cluster | TF 缺失 → dynamic_cloud 整帧丢弃 | `tf2_echo rm_frame livox_frame` |
| 聚类点满天飞 | 定位偏了，静态结构没被扣掉 | RViz 看 `/filter_map` vs `/livox/map` |
| 目标框对但位置差 1–2 米 | 投影偏 / 标定问题 | 看残差统计报告 |
| 位置每隔几秒跳一次 | `hard_reset_distance_m` 被反复触发 | 看是否有周期性错匹配 |
| 红蓝色反了 | `camera_color_order` | 改成 `bgr` 试试 |
| 界面卡顿、延迟越来越大 | B 阶段处理不过来，包堆积 | 看 `pending_replaced_total` |
| 回放能跑，实机不行 | 改了源码雷达配置但没 `colcon build` | 对比 src 与 install 下的 params.yaml |
| 前哨站存活一直判错 | ROI 没框对 / HSV 阈值 | 看 `outpost_binary_image` 调试图 |

## 8. 一套推荐的验证流程

改动算法后，按这个顺序验证（每一步失败就停）：

```text
1. 单元测试
   cd Main_ws && python -m pytest tests/ -v

2. 回放预检
   ./run_replay_test.sh Main_ws/config/test.yaml --preflight-only

3. 7 秒样例回放
   看：目标是否被框住、位置是否落在场地内、颜色是否对

4. 完整 9.9 分钟回放
   看：pending_replaced 是否持续增长（性能）、残差统计均值是否正常（标定）

5. 对比改前改后的 runtime_metrics.jsonl
   看：commit_fps 有没有下降、end_to_end_latency 有没有变差

6. 实机验证
   注意：实机读 install 副本，先 colcon build
```

## 9. 一个容易忽视的调试手段

`detection_pipeline.enabled: false` → 退回单线程串行路径（`_serial_main_loop_thread()`）。

**这不是"降级模式"，而是一个诊断工具**：

- 如果串行正常、流水线异常 → 问题在 A/B 交接（邮箱、epoch、年龄检查）。
- 如果两者都异常 → 问题在算法本身（检测或融合）。

因为串行路径逻辑更直白（取图 → 检测 → 融合 → 输出，一条直线），把问题从"并发问题"和"算法问题"里区分出来非常有效。
