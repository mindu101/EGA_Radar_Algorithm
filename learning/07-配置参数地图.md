# 07 · 配置参数地图

这个项目有 8 个 yaml，参数分散。这篇按「**你想改什么 → 去哪个文件改哪一项**」组织，而不是按文件罗列。

## 文件清单

| 文件 | 谁读它 | 作用 |
|---|---|---|
| `Main_ws/config/params.yaml` | Python 主程序 | **最重要**：模型、阈值、跟踪、融合、可视化、调试 |
| `Main_ws/config/device.yaml` | Python 主程序 | 相机采集参数、内参畸变、雷达外参矩阵 |
| `Main_ws/config/guess_pts.yaml` | `PointGuesser` | 长期丢失时的固定回退点 |
| `Main_ws/config/botsort.yaml` / `bytetrack.yaml` | ultralytics | 车辆跟踪器参数 |
| `Main_ws/config/test.yaml` / `test_full.yaml` | 回放启动器 | 同步回放配置 |
| `Lidar_ws/src/rm2026_lidar_launch/config/params.yaml` | ROS2 launch | **雷达管线全部参数**（含详细中文注释） |
| `Lidar_ws/src/rm2026_lidar_launch/config/lidar_extrinsics.yaml` | localization | 雷达初始外参（配准初值） |

> 小提示：`Lidar_ws` 那份 `params.yaml` 的注释密度是全仓库最高的，几乎每个参数都写了「影响：」。**想理解雷达侧行为，直接读那 240 行注释比自己啃 C++ 快。**

## 一、想调检测灵敏度

**文件**：`Main_ws/config/params.yaml`

```yaml
car_detector:
  img_size: 1280        # 输入缩放尺寸
  conf_thres: 0.3       # 车辆置信度阈值
  iou_thres: 0.5        # NMS IoU
  max_det: 10           # 最多保留几个车辆框

armor_detector:
  img_size: 192         # 装甲检测输入（每个车辆 ROI）
  conf_thres: 0.4
  iou_thres: 0.4
  max_det: 4            # 每个车辆 ROI 最多几个装甲

digit_detector:
  digit_confidence_weight: 0.70
  armor_confidence_weight: 0.30
  min_digit_confidence: 0.30            # 数字置信度下限
  min_combined_confidence: 0.55         # 组合置信度下限
  colored_anchor_min_combined_confidence: 0.30   # 彩色可作为身份锚点
  gray_anchor_min_combined_confidence: 0.40      # 灰色可作为身份锚点
  ignored_digit_index: 5                # 前哨站，丢弃
```

| 想做的事 | 改什么 | 副作用 |
|---|---|---|
| 漏检多 | ↓ `car_detector.conf_thres` | 误检增加，BoT-SORT ID 更乱 |
| 误检多 | ↑ `conf_thres` | 远处小目标更容易漏 |
| 装甲认不出来 | ↓ `min_combined_confidence` | 错误身份进入融合 |
| 身份错误多 | ↑ `min_combined_confidence` | 大量目标退化为灰甲/猜点 |
| 一辆车上多个装甲互相干扰 | ↓ `armor_detector.max_det` | 可能丢掉正确的那个面 |

⚠️ **`car_detector.conf_thres` 可以在 UI 里运行时调整**（`set_car_detector_conf_thres`），调完立刻生效，适合现场手感调参。其他阈值改 yaml 后要重启。

## 二、想调融合匹配的"松紧"

**文件**：`Main_ws/config/params.yaml`，`tracker.cascade` 节点。

```yaml
tracker:
  cascade:
    unknown_faction_fallback: "red"    # 裁判还没给阵营时的默认
    random_seed: 2026                  # 猜点随机数种子（可复现）

    bot_history:
      queue_size: 30                   # 每个 BoT-ID 保留几帧语义
      matching_window: 10              # 只用最近几帧算分布
      decay_tau: 0.5                   # 指数衰减系数
      association_ttl_frames: 30       # 多少帧不见就删除该 BoT-ID

    colored_triplet_match:
      max_ray_lidar_distance_m: 1.5    # 投影点—雷达点门限
      semantic_cost_weight: 2.0
      ray_distance_cost_weight: 6.0

    gray_match:
      max_ray_lidar_distance_m: 1.5
      semantic_cost_weight: 1.5
      track_distance_cost_weight: 2.0
      ray_distance_cost_weight: 3.0
      unseen_track_cost: 0.5           # 无历史的身份的固定代价
      side_cost_margin: 0.15           # 红蓝代价"几乎相等"的判定边界
      enemy_tie_bias: 0.05             # 同分时偏向敌方的程度

    history_lidar_match:
      max_distance_m: 2.0              # 预测位置—雷达点门限
      unmatched_cost: 100.0            # 虚拟列代价（允许不匹配）
      invalid_edge_cost: 1000000.0     # 非法边代价

    ally_fusion:
      feedback_timeout_sec: 0.15       # 己方反馈有效期
      max_lidar_match_distance_m: 1.5
      feedback_r_std_m: 0.0            # 完全相信己方反馈
      age_r_std_per_sec: 0.0
      update_kf_without_lidar: true

    position_kalman:
      default_dt_sec: 0.033333
      min_dt_sec: 0.001
      max_dt_sec: 0.20
      process_q_std: 2.0               # 过程噪声（越大越信新测量）
      lidar_r_std_m: 0.20              # 雷达测量噪声
      initial_position_std_m: 0.25
      initial_velocity_std_mps: 2.0
      hard_reset_distance_m: 2.5       # 超过这个跳变就重建滤波器

    loss:
      radar_guess_after_frames: 10     # 丢多少帧后允许纯雷达猜
      fixed_guess_after_frames: 30     # 丢多少帧后回到固定点

    guessing:
      enemy_only: true
      role_priority: ["hero", "standard_3", "standard_4", "sentry", "engineer"]
```

**这组参数的相互关系**（很重要，单独改一个容易出怪事）：

```text
min_combined_confidence ↑  →  有效彩色观测变少  →  更多目标走灰甲/历史/猜点
radar_guess_after_frames ↓ →  猜点变早  →  错点变多，但覆盖更全
process_q_std ↑            →  卡尔曼更信测量  →  抖动大、拖尾小
lidar_r_std_m ↓            →  更信雷达     →  同上
hard_reset_distance_m ↓    →  更容易重置   →  轨迹更跳，但不会"拉不回来"
```

假设有个 bug：某个身份每 3 秒跳一次位置。**先看 `hard_reset_distance_m`**——2.5m 的阈值意味着只要出现一次 2.5m 的错匹配，轨迹就会被硬重置，然后错位置会通过历史续接自我强化。

## 三、想调雷达点云处理

**文件**：`Lidar_ws/src/rm2026_lidar_launch/config/params.yaml`

### 3.1 配准（定位准不准）

```yaml
lidar_pipeline:
  startup_delay_sec: 2.0
  localization:
    backend: "gicp_ndt"          # gicp | ndt | gicp_ndt
    enable_registration: true    # false → 直接用外参，不做配准
    max_registration: 1          # ★ 关键：只配准 1 次
    continuous_registration: false
    accept_unconverged_result: true
    registration_interval_sec: 0.5
    fitness_threshold: 0.01      # 越小越严
    stable_required_count: 30
    enable_background_filter: true
    transform_smooth_alpha: 0.35
    max_translation_jump: 10.0   # 放宽以允许重置
```

| 现象 | 调什么 |
|---|---|
| 定位精度 10–20cm 上不去 | 确认日志里有 `fine NDT`（而不是只有 GICP）；检查 `ndt.fine.resolution` |
| 配准每次跑很久 | `max_registration` 保持 1；或关掉 `continuous_registration` |
| 雷达被碰后不自动恢复 | 降低 `registration_reset_inlier_ratio_threshold`（当前 0.90 已很敏感） |
| 定位偶发跳飞 | 降低 `max_translation_jump`；提高 `fitness_threshold` |
| 想完全不做配准（用固定外参） | `enable_registration: false` |

**`max_registration: 1` 的语义再强调一次**：跑完一次完整配准后永久停止，`background_grid_` 仍逐帧更新用于检测雷达是否被移动。见 [03-雷达管线三节点.md](03-雷达管线三节点.md) 1.4 节。

### 3.2 动态点提取

```yaml
dynamic_cloud:
  voxel_leaf_size: 0.1
  near_accumulate_time: 3      # 近端累积帧数
  middle_accumulate_time: 6
  far_accumulate_time: 6
  region_split_axis: "x"
  near_middle_split_position: 16.0
  middle_far_split_position: 22.0
  near_region_positive: false  # 坐标小的一端是近端
  near_map_distance_threshold: 0.05    # m²
  middle_map_distance_threshold: 0.04
  far_map_distance_threshold: 0.03
  main_roi: [0.3, 27.4, 0.3, 14.7, 0.1, 1.3]
```

| 现象 | 调什么 |
|---|---|
| 静态结构被当动态（鬼影点） | ↑ 区域阈值；检查定位是否偏 |
| 远处目标检不到 | ↑ `far_map_distance_threshold`；↑ `far_accumulate_time` |
| 目标位置拖尾明显 | ↓ 对应区域的 `accumulate_time` |
| 主场地外的点太多 | 收紧 `main_roi` 或加 `map_exclude_*_rois` |

### 3.3 聚类

```yaml
cluster:
  near_cluster_tolerance: 0.25
  near_min_cluster_size: 5
  near_max_cluster_size: 5000
  middle_cluster_tolerance: 0.25
  middle_min_cluster_size: 3
  middle_max_cluster_size: 5000
  far_cluster_tolerance: 0.25
  far_min_cluster_size: 3
  far_max_cluster_size: 5000
```

`min_cluster_size` 近端比远端严格（5 vs 3），因为近端点密度更高。
`max_cluster_size=5000` 主要用来过滤大块非目标动态结构。

## 五、想调相机采集

**文件**：`Main_ws/config/device.yaml`

```yaml
camera:
  acquisition_rate: 30.0
  exposure_time: 10000     # 微秒
  gain: 23.0
  width: 4024
  height: 3036
  camera_matrix: [...]     # 9 个值，注意是扁平数组
  dist_coeffs: [...]
```

现场经验：室外光照变化大，先调 `exposure_time` 再调 `gain`（增益噪声更大）。曝光太长会让运动目标有拖影，直接影响装甲检测。

```yaml
debug:
  camera_mode: "camera"        # camera | image | ros | replay
  camera_color_order: "rgb"    # ★ 通道顺序，红蓝搞反的元凶
  inference_video: true
  video_source: "demo/demo1.jpg"
  streaming_video: true
  timing_debug_enabled: true   # 耗时统计
  timing_ema_alpha: 0.2
  log_inference_fps: false
  performance_metrics:
    enabled: true
    output_path: "logs/performance/runtime_metrics.jsonl"
  tf_debug:
    enabled: true              # 发布相机位姿/目标 TF
    root_frame: "rm_frame"
    publish_target_tf: true
    publish_target_pose: true
    publish_rate_hz: 2.0

detection_pipeline:
  enabled: true                # ★ false → 退回单线程串行
  camera_timeout_sec: 0.10
  max_commit_age_sec: 0.20
  worker_join_timeout_sec: 5.0

lidar_fusion:
  enabled: true
  topic: "/livox/lidar_cluster"
  queue_size: 10
  max_snapshot_age_sec: 0.20
  mirror_for_blue: true
  field_length: 28.0
  field_width: 15.0
# 注意：飞行目标的话题不在 yaml 里，是代码默认值
# lidar_fusion.fly_topic  → "/livox/lidar_fly_cluster"（main_event_loop.py 里 .get 的兜底）
# lidar_fusion.fly_enabled → 缺省时回退到 enabled
```

| 想做的事 | 改什么 |
|---|---|
| 用录好的图片测（无相机） | `camera_mode: "image"` + `video_source` |
| 用 ROS 图像话题 | `camera_mode: "ros"` + `ros_image_topic` |
| 关掉 A/B 流水线排查问题 | `detection_pipeline.enabled: false` |
| 红蓝颜色反了 | `camera_color_order: "bgr"` |
| 噪声大但响应快 | ↓ `max_commit_age_sec`（更激进地丢旧帧） |
| 不想要 RViz 里的目标 TF | `tf_debug.enabled: false` |

⚠️ `detection_pipeline.enabled: false` 是一个很好的**排查手段**：如果串行模式正常、流水线模式异常，问题一定在 A/B 交接（邮箱、epoch、年龄检查）而不是算法本身。

## 七、想调可视化

```yaml
visualization:
  enabled: true
  single_view: true
  separate_detection_view: false   # 关掉以省一次全分辨率叠图
  update_hz: 30.0
  output_max_width: 1280           # ★ 后台先缩小再画框
  output_max_height: 960
  box_thickness: 5
  label_font_scale: 1.5
```

`output_max_width/height` 是性能关键：4024×3036 的图上画框再缩放会非常慢，所以后台线程先把图缩到 1280×960 再叠加。**如果你要提高显示清晰度，先想清楚这会让可视化线程变慢多少**（它虽然是异步的，但会抢 CPU）。

## 九、想调前哨站存活检测

```yaml
outpost_light:
  color: "blue"          # 前哨站灯的颜色（随己方阵营变）
  reverse: false         # 二值化取反
  alive_ratio_threshold: 0.03    # 亮区面积占比阈值
  hsv_thresholds:
    blue:  {h_min: 95,  h_max: 130, ...}
    red:   {h_min: 170, h_max: 10,  ...}   # 注意 170 > 10，代码里走了环形分段逻辑
    green: {h_min: 35,  h_max: 85,  ...}
    white: {h_min: 0,   h_max: 179, ...}
```

红色的 `h_min=170 > h_max=10` 不是笔误，HSV 色相是环形的，`_bi_image()` 里专门处理了这种情况（分两段 inRange 再 OR）。

这个判断结果只影响一个输入：`outpost_alive`，用于判断前哨站是否已经死亡（从而决定某些目标的重要性）。**如果前哨站判断常错，先看 `alive_ratio_threshold` 和 ROI 是否框对了。**

## 十、参数改动检查清单

改任何参数之前：

1. **确认改的是 yaml 不是 launch 的 default**（launch 里的 `get(key, default)` 只是兜底）。
2. **一次只改一个**，因为很多参数是耦合的（见第二节的相互关系图）。
3. **改完跑测试**：`Main_ws/tests/test_cascade_match_tracker.py` 是纯 CPU 的，几秒钟；`test_detection_pipeline_*.py` 测流水线语义。
4. **用回放验证**：`./run_replay_test.sh Main_ws/config/test.yaml`，有确定性输入才能比较改动。
5. **看耗时统计**：`timing_debug_enabled: true`，确认没有把某一步拖垮。
